# remocn

shadcn registry с готовыми анимациями, переходами и backgrounds для Remotion.

## Что это

Набор production-ready компонентов для создания видео в Remotion. Пользователи устанавливают компоненты через `npx shadcn add remocn/<component>` и собирают видео из готовых блоков.

## Целевая аудитория

Solo builders и маленькие команды (1-2 чел), фронтендер знакомый с экосистемой shadcn. Типичный сценарий: сделали продукт → нужно demo video → берут remocn.

## Архитектура

Плоское Next.js приложение в корне репозитория, пакетный менеджер — bun. Никакого монорепо, workspaces и turborepo.

- `app/` — Next.js App Router. `app/(home)/` — landing и standalone-страницы (`sponsors`, `changelog`), `app/docs/` — Fumadocs, `app/r/` — раздача registry-артефактов, `app/api/` — рендер и прочие endpoints
- `content/docs/` — MDX документации (fumadocs collection `docs`), `content/changelog/` — записи ченджлога (flat collection `changelog`)
- `registry/` — исходники компонентов: `remocn/` (анимации, переходы, backgrounds), `remocn-ui/` (UI-примитивы), `remocn-icons/` (иконки), `remocn-templates/` (готовые видео). У каждого неймспейса свой `registry.json`; `registry/__index__.tsx` — отдельный реестр превью для сайта
- `registry-artifacts/` — собранный shadcn-registry (`bun run registry:build`), коммитится в репозиторий
- `public/_previews/` — собранный реестр превью, в git не попадает. См. «Превью собираются отдельно»
- `components/`, `lib/`, `config/`, `hooks/` — код сайта

## Уровни компонентов

- **Primitives** — отдельные анимации, переходы, backgrounds
- **Compositions** — готовые сцены, собранные из primitives
- **Templates** — полные видео, которые можно установить и использовать as-is

## Ключевые решения

- Плоский namespace: `remocn/fade-in`, `remocn/intro-scene`
- Remotion — prerequisite, не bootstrap'им его
- Own your code (shadcn philosophy) — файлы копируются в проект пользователя
- Все компоненты пишутся с нуля на Remotion API (`useCurrentFrame()`, `interpolate()`, `spring()`)
- Вдохновляемся reactbits.dev идеями, но НЕ копируем код (их лицензия MIT + Commons Clause запрещает порт)
- Превью на сайте через `@remotion/player` — интерактивный плеер в браузере
- Лицензия: MIT

## Документация — источник правды для агентов

Доки описывают компоненты и для людей, и для AI-агентов. Скилл `remocn` не хранит свою копию каталога, а читает документацию по URL, поэтому страница компонента — единственное место, где живут его пропсы, пример и сигнал выбора.

- Каждый item из registry обязан иметь страницу с `component: <name>` во frontmatter. Исключения перечислены в `UNDOCUMENTED` в `lib/docs-meta.test.ts` и требуют причины — это либы, внутренние примитивы и sub-item'ы, свёрнутые в страницу контейнера. Иконки документируются галереей, а не страницей на штуку
- Frontmatter компонента: `component`, `vibe` (одно из семи значений в `lib/docs-schema.ts`), `length`, `useWhen`, `avoidWhen` и `askedAs` — списки строк в двойных кавычках. Поля машинные, на странице не рендерятся
- `askedAs` — 5–8 формулировок, которыми компонент попросит человек, не видевший каталога: пара коротких запросов в 2–5 слов, пара фраз «хочу…», пара про задачу сцены. Без имени компонента и без слов из `description` там, где есть бытовой синоним («subtitles», а не «captions») — поле ценно именно словарём, которого в описании нет. На английском, до 90 символов, без двойных кавычек внутри. По этим строкам работает поиск, см. «Поиск компонентов»
- `length` — кадры **собственного движения** компонента при 30fps: у перехода это значение для `linearTiming`/`springTiming`, у остальных — момент, когда анимация закончилась. Это нижняя граница `Sequence`, а не длина бита: холд сверху добавляется отдельно. Поэтому `length` намеренно расходится с `durationInFrames` в `config.ts` — там длина демо-композиции вместе с холдом. `"state-driven"` — компонент рендерится из пропа `state` и своей длительности не имеет
- В `avoidWhen` называй компонент-замену в бэктиках. Тест валит сборку, если такого имени нет в registry
- MDX-страница доков не содержит `import` и `export`. Коллекция `docs` компилируется в рантайме (`dynamic: true` в `source.config.ts`): страница собирается, когда её рендерят — по запросу в dev и во время пререндера в `next build`. Иначе первый запрос доков в dev компилирует все ~900 страниц. Компонент, нужный отдельной странице, регистрируется в `components/docs/mdx-page-components.ts`, общий для всех страниц — в `mdx-components.tsx`. Blog и changelog собираются бандлером, им импорты разрешены
- `bun test lib/docs-meta.test.ts` — блокирующий шаг CI, отдельный от основного прогона тестов (тот пока `continue-on-error`)
- Агентские артефакты генерируются из этого frontmatter: `/llms-components.txt` (роутер по всем компонентам) и `/docs/**.md` (страница как чистый markdown, см. `lib/mdx-to-markdown.ts`)

## Превью собираются отдельно

`registry/__index__.tsx` перечисляет ~900 превью, у каждого ленивый импорт компонента и конфига. Turbopack компилирует ленивые импорты сразу, поэтому с этим индексом в графе сайта первый запрос любой страницы с превью компилировал все превью. Теперь индекс собирает Bun, а сайт загружает результат по URL.

- `scripts/previews/build.mts` собирает индекс в `public/_previews/` за ~0,3 с: dev-сборка лежит в `dev/`, production — в `prod/`, друг друга они не затирают. Один набор файлов читают и браузер (`/_previews/…`), и сервер (с диска). Все скрипты названы по хешу содержимого. `react` и `remotion` в сборку не входят: превью берут их у страницы, список общих модулей — `lib/previews/shared-modules.ts`
- Код сайта импортирует `@/lib/previews` и никогда `@/registry/__index__`: экспорты те же. Тест в `lib/docs-meta.test.ts` это проверяет. Скрипты и Remotion Studio по-прежнему импортируют сам индекс
- `bun dev` (`scripts/dev.mts`) собирает превью, запускает `next dev` и пересобирает превью при сохранении их исходников. Открытая страница получает сборку по WebSocket и подменяет изменённые превью на месте, без перезагрузки (`lib/previews/hot.ts`). Ошибка сборки печатается в терминале `bun dev`, страница остаётся на последней удачной сборке
- `bun run build` сначала собирает превью (`bun run previews:build`), затем сайт. `next build` без собранных превью падает на пререндере с подсказкой. Пересобрать превью после `next build` и не пересобрать сайт нельзя: страницы ссылаются на прежний входной файл
- `registry/__names__.ts` — сгенерированный список имён превью, коммитится. Его переписывает любая сборка превью, когда меняются ключи `registry/__index__.tsx`; тест проверяет, что он не отстал
- Сервер загружает только конфиги. `load()` на сервере отклоняется: плеер с `lazyComponent={load}` монтируется после гидрации

## Поиск компонентов

Один поиск на два входа: `searchCatalog` в `lib/search/components.ts` обслуживает и MCP-тул `search_components`, и `/api/search` (диалог ⌘K в доках). Запрос — описание потребности на любом языке, а не только имя.

- Ранжирование гибридное (`lib/search/hybrid.ts`): лексический скор по `name`/`title`/`description`/`useWhen`/`askedAs` и семантика, слитые через reciprocal rank fusion. Слова держат точные имена, смысл — запросы, у которых с каталогом нет общих слов
- Семантика — локальная модель `multilingual-e5-small` в процессе сервера (`@huggingface/transformers`), без API-ключей и платы за запрос. Модель и размерность зашиты в `lib/search/model.ts`
- `bun run search:build` считает векторы (описание + каждая строка `askedAs`) в `.search/` и туда же кладёт модель. Каталог в git не попадает; Dockerfile собирает его перед `next build`. Нет индекса или модель не загрузилась — поиск молча работает по словам, поэтому в dev запускать сборку индекса не обязательно
- `/api/search` отдаёт результат в формате fumadocs: сначала гайды, которые запрос называет целиком (и только пара их строк), потом компоненты, потом остальные полнотекстовые совпадения (`lib/search/docs-merge.ts`)
- Аналитика поиска идёт в OpenPanel одним событием `search_performed` для всех, со свойствами `actor` (`human` / `agent`) и `surface` (`docs_dialog` / `mcp` / `api`). Человек: диалог (`components/docs/search-dialog.tsx`) шлёт события из браузера — запрос считается, когда на нём остановились (правила в `lib/search/dialog-session.ts`), плюс `search_result_selected` и `search_abandoned`. Агент: сервер шлёт `search_performed` из MCP-тула и из `/api/search` (всё, что пришло не из диалога) и `component_fetched` на `get_component` / `preview_component` — это аналог клика
- Текст поискового запроса агента пишется в аналитику (до 200 символов) — политика конфиденциальности (`app/(home)/legal/content.tsx`, «MCP server») это описывает. Брифы `plan_video` и пропсы `preview_component` не пишутся: расширять запись можно только вместе с правкой политики
- `bun run search:eval` меряет поиск на `evals/search/golden.json` (топ-1/5/10 для слов и для гибрида). Меняешь ранжирование, модель или правила `askedAs` — сверяйся с ним; новые запросы в эталон приветствуются

## Поле Describe в кастомайзере

Над контролами панели Customize — поле, куда пишут желаемый вид словами («slower, dark background, serif»), и чипсы пресетов. Логика — `lib/describe/`, эндпоинты — `app/api/describe/`.

- Ярусы по цене, первый, что объяснил запрос целиком, отвечает: парсер слов и значений EN/RU (`literals.ts`) → пресеты компонента и общие настроения (`moods.ts`) по смыслу через e5 из поиска (`MATCH_THRESHOLD` в `policy.ts`) → встроенная модель браузера (Chrome `LanguageModel`, только если уже скачана) → Claude Haiku 5.5 на сервере
- Ответ модели — JSON по схеме из контролов (`model-schema.ts`): вердикт `on_topic` и список `{ prop, value }`. Текстовые и списковые пропсы модели не даются, так что выпросить у неё код или текст некуда. Текст в пропсы пишется только из кавычек в запросе
- Защита: попытка переписать инструкции модели («ignore previous instructions») — страйк сразу. Просьба о коде или тексте («write me a program», «напиши сочинение») — страйк до модели, только если в запросе больше ничего не читается как вид и компонент сам не про код или сообщения; иначе решает модель. Её вердикт `on_topic: false` и отказ — тоже страйк. 3 страйка за 30 дней — бан на модель (не на сайт) на 30 дней. Посетитель — хеш IP с солью `DESCRIBE_IP_SALT` (без неё в production модель выключена), IPv6 по /64 (`client-key.ts`). IP берётся из последней записи `X-Forwarded-For`, которую дописал Traefik: порт приложения не должен торчать наружу мимо прокси. Ещё лимит в минуту (в памяти), 30 вызовов модели в сутки на посетителя, дневной бюджет `DESCRIBE_DAILY_BUDGET_USD`, кэш ответов на 30 дней, тело запроса до 8 КБ. Модель видит только текст запроса и значения пропсов, которые ей можно менять — копия посетителя в промпт не попадает
- Route handler'ы работают на серверной сборке React, где конфиги превью (они тянут Remotion) не грузятся. Поэтому контролы всех компонентов пишет в `.describe/controls.json` скрипт `scripts/describe/build-controls.mts` — после `previews:build` и после каждой пересборки в `bun dev`
- Состояние — Postgres через drizzle: схема `lib/db/schema.ts`, миграции в `drizzle/` (`bunx drizzle-kit generate` после правки схемы), сервер применяет их сам при первом запросе, которому нужна база (бесплатные ярусы базу не ждут). Нет `DATABASE_URL` или `ANTHROPIC_API_KEY` — поле работает без модели. Тесты гоняют store на PGlite
- Пресеты компонента — `registry/presets/<name>.json`, генерирует `bun run presets:build` через Batch API (`--submit`, потом `--collect --wait`; `--missing` для новых компонентов). Пресет — про вид и движение, не про контент; при загрузке каждый проверяется по контролам
- Поле скрыто от агентского моста (`data-agent-hidden`): агент меняет пропсы напрямую, а поле стоит денег
- Текст запросов, ушедших в модель, хранится в `describe_answers` без привязки к посетителю, тексты страйков — 30 дней с хешем. Это описано в политике (`app/(home)/legal/content.tsx`, «The describe field»): расширять запись — только вместе с ней

## Пропсы сцен Launch Pack

Сцены Launch Pack (typography, numbers, product scenes, logo stings, social, media, ui-blocks…) делят один набор пропсов. Новая сцена получает их сразу, а не отдельным проходом потом.

- Общие пропсы там, где они имеют смысл: `fontFamily` (основной шрифт копирайта; mono и логотип не трогаем), `ink` (основной цвет текста), `background` (сплошная заливка или `"transparent"`; на сцене с `GshGround` заменяет градиент), `scale` (передний план вокруг центра, фон на месте), `delay` (кадры до начала движения: `Math.max(0, useSceneFrame() - delay) * speed`), `speed`, `grain` (только где рисуется зерно), `logo` (только где рисуется знак remocn)
- `scale` — через локальный `ScaleLayer`, который при `scale === 1` возвращает `children` без обёртки. Лишний элемент даже без transform меняет дерево слоёв Chrome и сдвигает сглаживание
- Значения по умолчанию равны прежним константам: рендер с дефолтами не меняется ни на пиксель. Проверка — `bun run review:props` до и после правки и `bun scripts/diff-stills.mts <до> <после>` («tiny» — шум рендера, «DIFF» — регрессия)
- Конфиг: `...sceneControls({ font: "<Family>", grain })` после своих полей и перед `speed`; `ground: groundControl()`; цвет, который берётся из темы, — `{ type: "color", default: undefined }`, панель показывает Auto; `string[]` и кортежи строк — в `lists` рядом с `controls` (в схеме Remotion нет массива строк)
- Шрифт из панели превью грузит сам (`lib/previews/fonts.ts`) и отдаёт компоненту после загрузки: сцены меряют текст при монтировании

## Частота кадров

Тайминги компонентов записаны в кадрах при 30 fps, а композиция пользователя идёт на любой частоте. Компонент разницы не замечает: на 60 fps сцена длится столько же секунд и получает новые промежуточные кадры.

- Кадр и конфиг компонент берёт из `@/lib/remocn/frame-rate`: `useSceneFrame()` и `useSceneConfig()` вместо `useCurrentFrame()` и `useVideoConfig()` из `remotion`. Они отвечают на шкале 30 fps при любой частоте композиции: на 60 fps кадр идёт 0, 0.5, 1, 1.5, `fps` равен 30, `durationInFrames` — длина в кадрах 30 fps. На 30 fps значения те же, что у Remotion. Тест в `lib/docs-meta.test.ts` не пускает в registry прямой импорт этих двух хуков
- Все числа в кадрах остаются кадрами при 30 fps: константы сцены, `delay`, пропсы вроде `staggerFrames`, `length` в доках
- Что компонент отдаёт самому Remotion, считается в кадрах композиции: `from` и `durationInFrames` у `<Sequence>` и серий, длина перехода в `linearTiming`. Такие числа проходят через `useCompositionFrames()`: `<Sequence from={toFrames(24)}>`. Образцы — `registry/remocn/terminal-simulator` и демо переходов (`registry/remocn/beam-sweep`)
- И обратно: число, которое Remotion даёт компоненту, приходит в кадрах композиции. У презентации перехода это `presentationDurationInFrames`: перед сравнением с константами сцены оно переводится в кадры 30 fps через `useSceneFrameCount()`, иначе на 60 fps фазы перехода растягиваются вдвое. Образец — `registry/remocn/card-swipe-cover`. Проверка в трёх кадрах такую ошибку пропускает: переход занимает малую часть демо, его снимают плотно — `--at 0.4,0.425,0.45,…`
- Дробный кадр — норма. Целочисленная математика по кадру (`Math.floor(frame)`, индекс массива, `frame % n`) допустима там, где шаг задуман: печать по символу, смена слова. В остальных местах промежуточный кадр на 60 fps повторит соседний
- Шаблоны (`registry/remocn-templates`) несут свою частоту и пересчитывают кадры сами (`atFps`), хуки `frame-rate` им не нужны. Компоненту registry внутри шаблона длительности передаются в кадрах 30 fps
- **Сайт играет превью на 60 fps.** Конфиги (`fps: FPS`, `durationInFrames`) и `registry/__manifest__.ts` остаются в своих единицах, 30 fps; пересчёт делается в одном месте, `lib/previews/frame-rate.ts`: `atPreviewRate()` в плеере доков и `sitePreview(name)` для всего, что читает манифест. Новый `<Player>` на сайте берёт тайминг через них, а свои номера кадров (кадр-заставка, `seekTo`) умножает на `previewScale()`. Композиции лендинга считают в кадрах 30 fps через те же хуки `frame-rate`
- **`previewFps: 30` в `config.ts`** — для сцены, которую браузер пока не успевает рисовать на 60 fps: ровные 30 лучше дёрганых 45. На компонент и рендер поле не влияет. Ставится по замеру, снимается, когда сцена оптимизирована
- **Шаг плеера пропатчен**: `patches/@remotion%2Fplayer@<версия>.patch` (`patchedDependencies` в `package.json`). Плеер Remotion выбирал кадр по `performance.now()` с округлением вниз, и запуск, начатый в неудачный момент между обновлениями экрана, шёл сериями «кадр дважды — кадр пропущен». Патч берёт время из метки обновления экрана и добавляет половину его интервала. При обновлении `@remotion/player` патч переносится на новую версию (`bun patch @remotion/player@<версия>`); `lib/previews/frame-rate.test.ts` падает, если патч не применился. В Remotion Studio у пользователей патча нет: это их копия Remotion
- **Доки пишутся на 60 fps.** В блоке кода композиция — `fps={60}`, и всё, что отдаётся Remotion, записано в её кадрах, то есть вдвое больше числа из 30 fps. Пропсы компонента в кадрах и `length` во frontmatter остаются кадрами 30 fps. Навыки агента планируют раскадровку в кадрах 30 fps и удваивают числа в файле видео. Правило для читателя — раздел Frame rate в `content/docs/getting-started/installation.mdx`
- **Элемент для «Add to Studio»** получает длину клипа под композицию на 60 fps (`ELEMENT_FPS` в `scripts/build-elements.mts`): Studio вставляет число как есть, не зная частоты, и клип под 30 fps обрезал бы анимацию в композиции на 60
- **Плавность вживую** меряет `bun run audit:playback -- --names a,b --out out/playback`: превью проигрывается в Chrome в том же плеере, что на сайте, и считаются обновления экрана без нового кадра. `ok` — сцена держит 60 fps; `SLOW` называет причину: `script` (главный поток не укладывается в кадр), `pixels` (на четверти пикселей сцена успевает — дорого закрашивать: размытие, фильтры, тени, большой canvas), `paint` (дорого само количество: слои, цепочка SVG-фильтров, сотни узлов). Мерить на свободной машине, по одной сцене: два замера сразу отнимают кадры друг у друга. Новая сцена должна давать `ok`
- Проверка — два прогона аудита и сравнение: `bun run audit:jitter -- --names a,b --out out/fps/30 --at 0.25,0.5,0.75`, тот же с `--fps-scale 2` в `out/fps/60`, затем `bun scripts/compare-frame-rates.mts out/fps/30 out/fps/60`. `same` — картинка на 60 fps совпадает с 30 fps в те же моменты; `held in between` — промежуточные кадры повторяют соседние; `different` — тайминг зависит от частоты

## Расписание элементов (`timeline.ts`)

Расписание анимации живёт отдельно от рисования: чистая функция пропсов в `registry/remocn/<name>/timeline.ts`, компонент читает из неё каждый номер кадра. По расписанию remocn lab показывает анимацию по элементам (строка, слово, финал), а проп `timing` двигает, обрезает и растягивает их по одному. Анимация без `timeline.ts` работает как раньше, лаборатория покажет её одним клипом — переход постепенный.

- Модуль — `@/lib/remocn/timeline` (`registry/remocn/timeline`), ставится зависимостью, как `frame-rate`. `defineTimeline((props, { length }) => TimelineElement[])`; элемент — `id`, `lane`, `label`, `start`, `length`, опционально `follows` и `beats`. Все числа — кадры 30 fps на шкале сцены, после `delay` и `speed`: те по-прежнему действуют на всю анимацию, `timing` — внутри неё
- **Id элементов — публичный API.** Сохранённый `timing` ссылается на них: выпущенный id не переименовывается и не меняет смысл. Тип — template literal: `` `entry:${number}` | "finale" ``
- В `timeline.ts` переносится тот расчёт, что был в компоненте, почти дословно. Функция чистая: импортирует только `@/lib/remocn/timeline`, без React, Remotion, DOM, `Math.random`. Дефолты пропсов, от которых зависит расписание, и константы живут там же, компонент их импортирует. Экспортируемые хелперы длины (`wordStreamLength`) остаются экспортом компонента
- `length` элемента — его собственное движение (как `length` в доках) либо время до следующего элемента дорожки. Момент внутри элемента — beat: длительность или смещение от `start` (`roll`, `travel`, `settle`). `stretch` умножает `length` и все beats, явный `length` только обрезает. Элементы — в порядке времени; `follows` указывает на более ранний элемент, и элемент сдвигается вместе с его концом. Список, который идёт подряд (буквы, слова, строки), — цепочка: каждый следует за предыдущим
- Компонент: `useTimeline(schedule, props, length, timing)` до любых ранних `return`, затем `tl.get(id)`, `tl.lane(name)`, `e.start`, `e.end`, `e.beat("roll")`. `length` расписания — та же длина, что компонент брал раньше: обычно `durationInFrames * speed`; у сцен, где выход привязан к концу композиции без `speed` (`line-by-line-slide`), — `durationInFrames`. Проп `timing?: Timing<Id>` необязательный
- Кадр считается так же, как раньше: `frame - e.start` вместо `frame - i * stagger`, `[e.start, e.end]` вместо `[at, at + 12]`. Без `timing` картинка не меняется ни на пиксель: `bun run review:props -- --names a,b --out out/frames/after --cases '{"default":{},"slow":{"speed":0.5},"odd":{"speed":1.7}}' --defaults --at all --scale 1` до и после правки (до — из отдельного worktree на прежнем коммите: правка во время сборки бандла попадёт в эталон), затем `bun scripts/diff-stills.mts out/frames/before/default out/frames/after/default` по каждому темпу. Партия из десятка компонентов в трёх темпах рендерится за минуту. Расхождение — баг переноса, эталон не подгоняется. Если сцена расходится и сама с собой (тот же код дважды: 3D-перспектива, размытие на GPU), сверяй с `--concurrency 1`
- Расписание, которое зависит от измерений (шрифт, DOM), а не только от пропсов, не переносится: компонент остаётся без `timeline.ts`
- Компонент с `timeline.ts` ставится папкой: `components/remocn/<name>/index.tsx` и `timeline.ts` (в `registry.json` два файла и `@remocn/timeline` в `registryDependencies`), путь импорта прежний. Элемент для «Add to Studio» встраивает `timeline.ts` в один файл
- Тест в `lib/docs-meta.test.ts` проверяет, что компонент с `timeline.ts` вызывает `useTimeline`, что `timeline.ts` ничего лишнего не импортирует и что расписание детерминировано, в порядке времени и с уникальными id

## Движение без дрожания

Chrome округляет до целого пикселя в двух местах. Всё, что медленно едет через любое из них, стоит несколько кадров, потом прыгает на пиксель; строки одного блока прыгают в разных кадрах, и блок дрожит. Новая сцена пишется сразу без этого, а не чинится потом.

- **Вёрстка.** Базовая линия текста (по вертикали) и края блока с фоном, рамкой или тенью округляются в координатах самого элемента. Поэтому путь задаётся только через `transform`: `top`, `left`, `margin`, `gap` и reflow от растущего соседа анимировать нельзя — вёрстка держит место покоя, сдвиг идёт в `translate`. `Math.round` на анимируемой позиции — то же самое вручную
- **Растр.** Глиф встаёт на целый пиксель экрана по вертикали, пока матрица выровнена по осям. Текст под `scale` или `translate` (и SVG-текст, двигаемый атрибутами) щёлкает; блоки, картинки и SVG-фигуры под `transform` сглаживаются и едут плавно. Лекарство — наклон, слишком малый, чтобы его увидеть: он снимает текст с сетки. Наклоняется только текст: рамка, линия или фотография под наклоном видны ступенькой
- **`useGlide()` из `@/lib/remocn/glide`.** Компонент только помечает `transform`, который несёт текст, и сообщает, движется ли он: `` `scale(${k})${glide(moving)}` ``. Метка — единичная матрица (одна в покое, две в движении), сама она ничего не меняет. После каждого кадра модуль даёт каждому блоку текста под меткой CSS-свойство `rotate`: вокруг центра блока, на наименьший угол, при котором матрица до экрана наклоняет `x` в `y` на 0,6/1024 пикселя экрана (порог Chrome — 0,5/1024), и в ту сторону, куда сцена уже повёрнута сама. Угол считается из матриц, поэтому компонент не знает ни масштаба плеера, ни своего: никаких `0.05`, `useCurrentScale` и деления на масштаб. Помечается любой `transform` с текстом и на любой скорости: от 0,5 до 2 px за кадр текст без наклона шагает неровно (1, 1, 0, 1). Образец — `registry/remocn/achievement-pop`
- **Метка стоит на каждом кадре, пока элемент смонтирован**: `transform` нельзя убирать, когда сдвиг равен нулю. Текст наклонён, пока `transform` над ним движется, и остаётся наклонён в покое, если покоится не на пиксельной сетке — под масштабом, под сдвигом на дробь пикселя, в плеере меньше композиции. Снять наклон там значит уронить строку на ближайший целый пиксель, до половины пикселя за кадр, и вернуть её обратно при следующем движении
- **Одна позиция в вёрстке на всю жизнь элемента.** Вёрстка округляет базовую линию, `transform` — нет, и кадр, где одно сменяет другое, прыгает на разницу. Элемент раскладывается там, где он окончательно останавливается, и всюду ещё доезжает через `translate`; в конечной точке это `translate(0)`, и кадр совпадает с тем, что дала бы вёрстка. Образец — `registry/remocn/crew-of-one`
- Метку модуль ищет только в инлайновом CSS `transform`. SVG-текст, который двигают атрибутами, помечается на стиле внешнего `<svg>`; наклон получает каждый `<text>`, вокруг своей середины. Текст внутри `mask` и `clipPath` сам повернуться не может, за него наклоняется весь рисунок. Текст в настоящей перспективе модуль не трогает: Chrome рисует его на отдельном слое. Сдвиг только по x метки не требует
- Под наклоном буквы всё равно стоят на сетке в четверть пикселя экрана — это предел Chrome для текста мельче ~160 px. Вдвое мельче шаг делает только рендер с `--scale 2`
- Кадр покоя совпадает с прежним попиксельно там, где текст стоит на сетке. Где он покоится под масштабом или дробным сдвигом, строка нарисована в точной позиции и с наклоном: такой кадр отличается намеренно, аудит пишет про него `lean kept`. `carried` — в кадре промежуточного покоя строка стоит там, куда её принёс `translate`, а вёрстка раньше округляла это место иначе, до пикселя
- `will-change: transform` на тексте запрещён: слой возит одну текстуру, она зависит от кадров, которые вкладка нарисовала раньше, а `npx remotion render` делит кадры между вкладками — соседние кадры расходятся до пикселя, и текст мылится. На фотографии без текста слой, наоборот, нужен: без него качество пересчёта картинки зависит от истории вкладки (`registry/remocn/reel`). `will-change: opacity`, `backface-visibility`, `translateZ(0)`, `text-rendering` и `skewX` на прилипание текста не влияют вовсе
- Рост через `width`/`height` (полоса, панель) тоже шагает по пикселю, но читается как рост и не правится: `scale` и `clip` меняют вид скруглений
- **Блок, который раскрывается в колонке, прижатой к низу** (чат, лента, ответ ассистента). `grid-template-rows: Nfr` и анимируемый `maxHeight` толкают вёрсткой всё, что выше. Блок раскладывается раскрытым на всю свою жизнь, обрезается снизу через `clip-path` и вместе со всем, что выше, сдвигается `translateY` на ещё не открытую высоту; в покое это `translateY(0)`. Высоты читаются в `useLayoutEffect` из `getComputedStyle` (трансформы на неё не влияют), а кадр держит `delayRender`, пока не пришли шрифты: без этого кадр, отрендеренный отдельно, меряет текст в запасном шрифте. Дорожка `Nfr` при высоте `p` показывает верхние `p * p` контента — обрезка должна это повторять. Образцы — `registry/remocn/channel-reactions`, `registry/remocn/ai-answer-sources` и `registry/remocn/voice-agent`
- Проверка — `bun run audit:jitter -- --names a,b --out out/jitter/x` (счёт щелчков по причинам и элемент-виновник в `details/<name>.json`). С `--base <папка прогона до правки> --stills` печатает вердикт «до → после» и сверяет попиксельно кадры, где ничего не движется. Скриншоты для счёта не нужны, одна вкладка — на все ~900 превью уходит около 40 минут. Меряются пропсы по умолчанию; другой темп проверяется через `--props '{"speed":0.5}'` на обоих прогонах
- Компонент готов, когда `ok` печатают два прогона с `--strict` (к щелчкам добавляются неровные шаги, прыжки при смене наклона и текст на слое `will-change: transform`): при полном размере и с `--shown 0.5` — так сцену показывает плеер вдвое меньше композиции. `--tabs 4` рендерит кадры в одной вкладке и в четырёх и считает расхождения: кадр не должен зависеть от того, что вкладка рисовала до него. `snaps N` — кадры, где наклон появился или исчез у текста, стоящего не на сетке, либо в том же кадре, где сменилась его позиция в вёрстке; `snapAt` в деталях называет кадр, текст и причину. `one-off N` — одиночные шаги: текст стоит в кадре до и в кадре после (строка перевёрсталась, когда сменился её текст); это не движение, и в вердикт они не входят. Модель аудита сверена с пикселями: `bun run audit:jitter-lab -- --lab cures|layers|angle|subtle` рендерит строки текста под каждым лекарством (`src/remotion/jitter-lab/`) и читает из кадров центр масс каждой буквы. Все цифры этого раздела сняты на macOS; на новом Chrome или другой платформе лабораторию стоит прогнать заново

## Changelog

Любая ветка, которая добавляет или заметно меняет компоненты registry, обязана содержать запись ченджлога — в том же PR, что и сама фича.

- Одна запись = один файл `content/changelog/<YYYY-MM-DD>-<slug>.mdx`. Дата в имени файла — дата мержа
- Frontmatter: `title`, `date`, плюс опциональные `video` и `videoPoster` (без кавычек, без `: ` внутри значений). `date` парсится в JS `Date`; `video`/`videoPoster` — полные URL на внешний видео-хостинг (`https://` не ломает YAML, там нет `: `)
- Запись = веха, а не PR и не календарный день
- Заголовки: `h1` и `h2` принадлежат странице (`h2` рендерится из `title`). Внутри тела — только `h3` для групп `New components` / `Improvements` / `Fixes`
- Живое превью: `<ChangelogPreview name="component-name" />`, где `name` — ключ из `registry/__index__.tsx`. Опционально
- Ссылки на доки компонентов приветствуются: `[Zoom Blur](/docs/transitions/zoom-blur)`
- Весь текст — на английском
- Опубликованные записи не переименовываются: имя файла — это якорь (`/changelog#2026-07-08-transitions-revamp`), которым делятся

Два вида просмотра — `/changelog` (текст) и `/changelog/video` (лента роликов), обе строятся из одной коллекции.

- В ленту попадают только записи с полем `video`. Нет поля — записи в видео-ленте просто нет, сборка не падает
- Видео — готовый веб-файл mp4 по внешнему URL. Хранение, компрессия и постеры — на стороне видео-сервиса, сайт их не делает
- CDN-конвенция: `video: https://cdn.remocn.dev/videos/<name>.mp4`, `videoPoster: https://cdn.remocn.dev/posters/<name>.png`. `<name>` произвольный и не обязан совпадать со slug записи — маппинг живёт во frontmatter. Поля пишутся парой: есть `video` — есть и `videoPoster`
- Плеер: `muted` + `playsInline` + `loop`, автоплей только у самого видимого ролика, остальные с `preload="none"`. При `prefers-reduced-motion` автоплей глушится

## UI docs-сайта на ui-sdk

Контролы кастомайзера (`components/docs/blocks/controls/`) и панель вокруг них собраны на `@ui-sdk/react`. Агентский мост ui-sdk (`createAgent`, WebMCP) видит только ui-sdk компоненты, поэтому голые `<button>`, `<input>` и `role="slider"`-дивы там не пишем.

- Перед работой с ui-sdk: скилл `ui-sdk`, затем `node_modules/@ui-sdk/react/docs/llms.txt` и страницы нужных компонентов из `docs/components/`. Версия beta, пинится точно
- `web.css` не подключаем — стили наши, Tailwind по `data-slot` и state-атрибутам. `@layer ui-sdk;` стоит первой строкой `app/globals.css`
- `components/ui/*` (shadcn на base-ui) остаётся как есть
- Тесты компонентов — vitest + jsdom (`bun run test:dom`, файлы `components/**/*.test.tsx`); `bun test` их игнорирует через `bunfig.toml`
- Мост для браузерного агента (WebMCP) — `components/docs/agent/`: грузится лениво из панели Customize, только где есть `document.modelContext` (в dev всегда, как `window.remocnAgent`). Агент меняет значения, сворачивает группы и жмёт Reset, Undo и Redo; кнопки, которые пишут в буфер обмена или уводят со страницы, помечены `data-agent-hidden`, а `allowStep` не пускает к остальным `button`. Новая кнопка в панели — реши, нужна ли она агенту, и поправь тест в `customize-panel.test.tsx`

### Эталон: shuding/spec-01

[github.com/shuding/spec-01](https://github.com/shuding/spec-01) — кит на ui-sdk от автора ui-sdk, считаем его best practice. Перед тем как считать код на ui-sdk готовым, найди в `registry/hardware/ui/` spec-01 компонент на том же примитиве и сверь. Стили там на plain CSS через `data-kit`, у нас Tailwind — это расхождение намеренное, сверяем композицию и поведение, не стили. Их ui-sdk — nightly-сборка, у нас beta: API сверяй с нашими `docs/`.

Чек-лист:
- Имя контрола даёт видимый `FieldLabel` внутри `Field` (slider, number input, text, textarea). `aria-label` — только когда видимого текста нет или он живёт внутри триггера (Select)
- Внутри `Field` не передавай контролу свой `id`: он перебивает id от `Field`, и `<label for>` указывает в пустоту. `Field` оборачивает `NumberInput` снаружи (как в наших docs); в spec-01 `Field` внутри `NumberInput` плюс `aria-label` — у нас так `for`/`id` расходятся. Связку проверяй рендером в HTML (`renderToString`) или тестом по `getByLabelText`
- Значение показывает часть ui-sdk (`SliderValue` с `format`), а не своя копия текста
- Декор (шкалы, тики) — `aria-hidden` span прямо внутри `SliderControl`, не внутри `SliderTrack`
- Свой pointer-код поверх ui-sdk допустим только как расширение: порог сдвига, `setPointerCapture`, проверка `pointerType`, итог — через тот же controlled `onValueChange`. Комментарий объясняет зачем
- Попап (`*Content`): сбросить `right`/`bottom` и держать высоту по контенту (`right-auto bottom-auto h-fit max-h-(--available-height) overflow-y-auto`) — иначе в Safari UA-шный `inset: 0` растягивает попап до низа экрана
- Перетаскиваемый слайдер показывает нажатие, а не focus ring
- ui-sdk перезаписывает `data-slot` своим значением (`button`, `switch`…). Свой хук для CSS/тестов — отдельный атрибут (`data-copy-button`), не `data-slot`. Переводя элемент на ui-sdk, grep'ни его старый `data-slot` по CSS
- Комментарии — только «почему»: браузерный квирк, компромисс, правило APG
